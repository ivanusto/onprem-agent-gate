# Where the gate sits in ISO/IEC 27001:2022 Annex A

Not a compliance claim. The table says which control each piece of this
repo (and the Day 26 to 28 pieces it leans on) gives an auditor something
to look at for, and what it does not. Control titles are from ISO/IEC
27001:2022 Annex A (the standard text itself is paid; only titles and the
gist are quoted here).

| Annex A | Control | What the gate gives you | What it does not |
|---|---|---|---|
| 5.15 | Access control | Deny by default: a tool exists only if tools.json lists it, a call passes only if a record names the agent and the asset | Nothing about access by people; that is sshd, sudo and the NAS |
| 5.16 | Identity management | The agent is an ssh key with a forced command; `principal` in config.json is the name records use in `agent:` | Key rotation and revocation are manual (remove the authorized_keys line) |
| 5.17 | Authentication information | The gate's own key to targets never leaves the collector; the agent holds no credential to any target | The key file's protection is the collector's filesystem, nothing more |
| 5.18 | Access rights | Rights are per record: `agent:` (who), `assets:` (where), `status`/window/begin mark (when), level (how far). They expire with the window and with `change-mark.sh end` | No review cycle of standing rights, because there are none: every right comes from a record |
| 8.2 | Privileged access rights | L2 and L3 need an open window and a begin mark; L3 needs one named human, single use, 10 minutes, bound to the exact argv (action hash) | The approval is a file on the collector; a root on the collector could forge one (see 8.15) |
| 8.3 | Information access restriction | Read tools are bounded (200 rows, 500-character queries, listed units only) and still need a record | Read results reach the model; what the model does with them is outside the gate |
| 8.5 | Secure authentication | ssh keys only, `restrict` on every line, `from=` on the target side | No MFA on the approval step; `sudo` as the named human is the second factor the site has |
| 8.9 | Configuration management | tools.json and config.json are files in git; a change to them is a change record like any other | The gate does not verify its own files' hashes at start |
| 8.15 | Logging | One chained record per decision (sha256 over previous hash and canonical JSON) and one journal line per record (seq, cr, tool, level, decision, rc, hash prefix) uploaded to VictoriaLogs and archived to WORM daily (Day 21) | The chain file is on the collector; its integrity argument is the WORM copy of the hash prefixes (`gatectl verify --vl`), not the file itself |
| 8.16 | Monitoring activities | `agent-gate.prom`: pending approvals, stop state, chain ok, denials per hour; five rules in onprem-metrics | Alerts say that something happened, the reasons are in `gatectl tail` and the audit report |
| 8.32 | Change management | Every call names a record; L2/L3 only inside the window a human opened; Day 27's audit report attributes the gate's lines to that window and lists any outside it | The record's content (is this change sensible) is still a human's judgement |
| 5.23 | Information security for use of cloud services | Not applicable here: the model runs on site (DGX Spark) or the client is a workstation; no site data leaves through the gate | If the agent's model is a cloud API, the read results do leave; that is a decision for the record's `影響` section |

## ITGC reading

For an ITGC reviewer the same pieces map to the usual four: access to
programs and data (5.15 to 8.5 above), program changes (8.32 with
onprem-changes), computer operations (8.16, the Day 19 to 20 stack), and
program development (not applicable, the gate changes nothing in code).
The evidence an auditor would sample is the same three things Day 26 to 28
already produce: the record in git, the marks and gate lines in the WORM
archive, and the Prometheus rule state at the time.

## Honest boundaries

- The gate decides on what it can read: a record, a window, a state file,
  a regex. It does not understand the command. `systemctl restart
  corosync-qnetd.service` is L2 because a human put it under L2 in
  tools.json.
- The model can be wrong or be talked into asking for something. The gate
  answers that with DENY and a reason, and the reasons are audited. It does
  not stop the model from reporting nonsense to the operator.
- One host runs the gate, holds the chain and the approvals. The
  hackathon design this repo descends from split control plane and
  enforcement; here they are one process on the collector, and the WORM
  copy of the journal is what makes the chain more than a file root can
  edit.
